# Hangtag architecture

Hangtag is an installable web app (PWA) for running a shop from a phone: products, stock, billing,
receipts, returns, customers and reports. Every device keeps a full local copy, works offline, and syncs with a
Supabase (Postgres) database when online.

The app runs as **native ES modules**, served as-is by GitHub Pages. There is no framework and no build step at
runtime. `npm run build` only checks the code and updates the service worker's file list (see [Build](#build)).

## Layers and responsibilities

| Layer | Responsible for | Must not |
|---|---|---|
| **Presentation** (`features/*/pages`, `features/*/components`, `app/events`) | Markup, reading forms, loading states, showing errors and toasts, calling use cases | Call Supabase; hold business rules beyond simple input handling |
| **Application** (`features/*/use-cases`, `features/*/services`) | Workflows (SaveProduct, SaveShopProfile, RecordStockOperation, Checkout…): apply domain rules, then call repositories and ports; read models over state | Import `infrastructure/` or `app/` (use ports) |
| **Domain** (`domain/`) | Rules: variant price/cost inheritance, catalog upgrades, SKU/barcode uniqueness, product/profile/settings validation, stock operations, bill totals, invoice numbers, stock levels | Use browser APIs, the state store, Supabase, or anything outside `domain/` and `shared/` |
| **Infrastructure** (`infrastructure/`) | Supabase client, gateway, mappers and error mapping; localStorage; files; repository implementations | Import `features/` or `app/` |
| **Shared** (`shared/`) | Helpers every layer may use: config, ports registry, state store, errors, logger, UI primitives | Import any other layer |
| **Composition root** (`app/`) | Start-up order, providing implementations to ports, global event wiring | Hold business rules |

### Dependency direction

```text
            app/  (composition root: may import everything; provides the ports)
             │
             ▼
 features/  ──►  domain/  ──►  shared/
     │                           ▲
     └── use(port) ── shared/di ─┘
                        ▲
                        └── provided by app/container.js from infrastructure/  ──►  domain/, shared/
```

| Layer | May import |
|---|---|
| `shared` | `shared` |
| `domain` | `domain`, `shared` |
| `infrastructure` | `infrastructure`, `domain`, `shared` |
| `features` | `features`, `domain`, `shared` (never `app`, never `infrastructure`) |
| `app` | anything |

`scripts/check-architecture.mjs` enforces these rules. It runs in `npm run build`, `npm run check` and the unit tests,
and fails on any violation:

- An import that crosses layers the wrong way, or that points at a missing file.
- Supabase or network access (`sbClient.from/auth/rpc/channel`, `.from('hangtag_…')`, `fetch(`) outside `infrastructure/`.
- Browser APIs or the state store in `domain/`.
- `localStorage`/`sessionStorage` outside `infrastructure/storage/`.
- `window.HANGTAG_CONFIG` or `window.__HANGTAG_TEST__` read outside `shared/config/app-config.js`.
- `console.*` outside `shared/logging/logger.js`.
- Import cycles (none today).

## Ports: how features reach infrastructure

Features depend on **ports** (named contracts), never on implementations. The registry is `shared/di/services.js`:

- `provide(name, impl)` registers an implementation.
- `use(name)` returns it, and throws an error naming the port when nothing was provided. It looks the port up on every call.
- `override(fakes)` and `resetPorts()` are for unit tests.

The contracts are JSDoc typedefs in `shared/di/ports.js`.

```js
// app/container.js: installContainer() is the first thing main.js runs
provide("storage", LS);
provide("files", { saveFile, fileToThumb });
provide("session", { signOut, enterApp });
provide("cloud", createCloudGateway({ getClient: () => store.sbClient, url: sbUrl, key: sbKey, storageKey: AUTH_STORE }));
const outbox = { enqueue, dropQueued };
provide("productRepository", createLocalFirstProductRepository({ store, persist: { saveCatalog, saveMoves, saveImgs, saveSbQueue }, outbox }));
provide("stockRepository", createLocalFirstStockRepository({ store, persist: { saveMoves, saveCatalog }, outbox }));

// a use case depends on the contract (features/products/use-cases/product-lifecycle.js)
export const archiveProduct = (pid, on) => productRepository().setArchived(pid, on);
```

| Port | Implementation | Reached through |
|---|---|---|
| `storage` | `infrastructure/storage/local-storage.js` | `shared/state/persistence.js`: one saver per state slice, plus `storage` (`get`/`set` JSON, `getRaw`/`setRaw`/`remove`) |
| `files` | `infrastructure/browser/files.js` | `use("files").saveFile(name, data, type)`, `use("files").fileToThumb(file, size)` |
| `renderer` | `app/navigation.js` (provided by `installNavigation()`) | `shared/ui/render.js`: `renderAll()`, `setTab(tab)` |
| `session` | `features/auth/services/session.js` | `shared/ui/session-actions.js`: `requestSignOut()`, `requestEnterApp(firstTime)` (avoids an import cycle between sign-in and shop setup) |
| `cloud` | `infrastructure/supabase/cloud-gateway.js` | `use("cloud")` in `features/sync` (uploads, downloads, live updates), `features/auth` (sign-in) and `features/shop` (profile) |
| `productRepository` | `infrastructure/repositories/local-first-product-repository.js` | `features/products/repositories/product-repository.js` |
| `stockRepository` | `infrastructure/repositories/local-first-stock-repository.js` | `features/inventory/repositories/stock-repository.js` |
| `barcodeService` / `qrCodeService` | `infrastructure/codes/` | product editor code previews, stickers |
| `documentExtractionService` | `infrastructure/extraction/bill-extractor.js` → Edge Function `extract-bill` | `features/inventory/use-cases/import-supplier-bill.js` |
| `barcodeScanner` | `infrastructure/scanner/camera-scanner.js` | `features/sales/components/camera-scan.js` (Sell → Scan), rules in `domain/sales/scan-rules.js`, `use-cases/scan-to-cart.js` |
| `inventoryImportService` | `infrastructure/repositories/local-first-stock-import.js` → RPC `hangtag_import_stock` | `features/inventory/use-cases/import-supplier-bill.js` |

`app/main.js` calls `installContainer()` and `installNavigation()` before anything reads storage or renders. The
rest of start-up keeps the original order.

### Database access pattern

```text
ProductEditor (component: reads the form)
  → saveProduct (use case: domain validation, variants, opening-stock moves)
    → productRepository (port)
      → local-first product repository (infrastructure): update the store, persist to this device, enqueue uploads
        → outbox (features/sync/services/outbox.js), in order, with retries
          → cloud port → cloud-gateway.js → mappers.js → hangtag_products / hangtag_variants / hangtag_stock_moves
```

- **Local-first.** Every write lands in local state first and is saved on this device, so the app works offline.
  It is also queued in the **outbox**, which uploads in order, retries on failure and never drops work.
- **Downloads.** `features/sync/services/pull.js` (full download) and `remote-events.js` (live updates) merge cloud
  data into local state through the `cloud` port. The cloud wins, except for changes still waiting in this device's
  queue.
- **One Supabase gateway.** Every Supabase call (tables, auth, realtime, RPC) is a method of
  `infrastructure/supabase/cloud-gateway.js`. Row ↔ record mapping lives in `mappers.js`. The gateway reads the
  client on every call, so signing in again or a test can swap it.
- **The database is the authority.** Row-level security (`owner_id = auth.uid()`), unique SKU/barcode per shop, the
  return-quantity trigger and foreign keys live in `supabase/schema.sql`. Frontend checks only give quick feedback.

## State

One store object (`shared/state/store.js`) holds the app's state. `app/state-init.js` restores it at start-up.
Saving goes through `shared/state/persistence.js` and the `storage` port, one saver per slice. The keys and JSON are
unchanged from the single-file app:

- Local data: `rc_catalog`, `rc_imgs`, `rc_moves`, `rc_returns`, `rc_customers`, `rc_settings`.
- Sales: `rc_local` + `rc_dirty`, and `rc_pend`.
- Cart and preferences: `rc_cart` + `rc_disc` + `rc_cartcust`, and `rc_prefs`.
- Sync and account: `hangtag_sb_queue`, `hangtag_profile`, `hangtag_last_sync`.

When the device's storage is full, `persistLocal()` says so once.

| Kind | Keys (examples) | Written by |
|---|---|---|
| Session / auth | `authUser`, `profile`, `authSettings`, `signingIn`, `emailMode` | `auth`, `shop` |
| Cloud connection | `sbClient`, `sbStatus`, `sbRealtimeChannel`, `sbOfflineQueue`, `lastSyncAt`, `syncing` | `sync` |
| Local data (this device's copy of server data) | `catalog`, `imgs`, `moves`, `returnsMap`, `customers`, `settings`, `localDays`, `remoteDays` | Use cases, repositories and `sync` merges (see the exceptions below) |
| Form state | `editor`, `stockOp`, `retState`, `custForm`, `pick` | The component that opened it |
| UI state | `prefs` (tab, period, filters), `sellQuery`, `prodView`, `billOpen`, `cart`, `disc`, `cartCust` | The owning page or component |
| Derived | `_d`: the stock ledger read model, rebuilt by `invalidate()` | `features/inventory/services/ledger.js` |

Rules for new code:

- Only use cases, repositories and `sync` write local data.
- Presentation writes only form state and UI state.
- Derived values (stock on hand, totals) are computed, never stored.

### Known exceptions (carried over from the single-file app)

The refactor moved code without changing behaviour. These places still write local data or queue uploads
directly, instead of going through a use case and a repository. **When a later phase changes one of them, move
the write behind a repository first.**

| Where | What it writes directly |
|---|---|
| `features/sales/use-cases/checkout.js` | Sales, void/unvoid, the upload queue. It also closes the bill sheet and shows the receipt, so its UI steps should move to the component. |
| `features/returns/components/return-sheet.js` | Returns, and queues their upload |
| `features/customers/components/customer-picker.js` | New customers, and queues their upload |
| `features/products/components/colour-groups.js` | Merges products into colour groups (catalog, moves, product uploads/deletes) |
| `features/products/services/examples.js`, `features/products/services/catalog.js` | The example catalog, and the catalog upgrade on load |
| `features/backup/services/backup-file.js` | Restores every slice from a backup file |
| `features/shop/use-cases/save-billing-settings.js`, `app/events/dom-events.js` (dismissing a grouping suggestion) | Settings, and queues their upload (no settings repository yet) |

Also: `saveShopProfile` calls the `cloud` port directly, because the profile must be saved online before the app
opens. The gateway's auth and profile methods return supabase-js results (`{ data, error }`) rather than throwing
an `AppError`.

## Validation

- **Domain rules** live in `domain/`:
  - `domain/catalog/product-validation.js`: name, price, cost, stock, SKU/barcode uniqueness.
  - `domain/shop/profile-validation.js`: required fields, phone, GSTIN.
  - `domain/shop/settings-validation.js`: invoice prefix, GST rate, low-stock threshold.
  - `domain/inventory/stock-operation.js`: quantities and cost per piece for stock in and adjustments.
- **Format checks** live in `shared/validation/` (email, phone, GSTIN).
- **Use cases** validate first. On failure they return `{ error }` with a message written for the person, which the
  form shows (`saveProduct`, `recordStockOperation`, `saveBillingSettings`). `saveShopProfile` throws an `Error`
  whose message is shown.
- **The database** repeats every rule that must hold even if the app is bypassed, and is the authority.

## Errors and logging

- `shared/errors/app-error.js` defines `AppError`. Each one carries:
  - a `code`: `NETWORK`, `AUTH`, `PERMISSION`, `VALIDATION`, `CONFLICT`, `NOT_FOUND`, `OUTDATED_DATABASE`, `STORAGE_FULL`, `NOT_CONFIGURED` or `UNKNOWN`;
  - a `message` written for people;
  - the original `cause`, kept for logs.

  `userMessage(e, fallback)` picks what to show.
- `infrastructure/supabase/errors.js` (`toAppError`) maps Supabase, Postgres and network errors to an `AppError`:

  | Error | Code |
  |---|---|
  | Failed fetch | `NETWORK` |
  | `42501` (RLS) | `PERMISSION` |
  | `23505` | `CONFLICT` |
  | JWT or `PGRST301` | `AUTH` |
  | Missing table or column | `OUTDATED_DATABASE` |
  | `23514` / `P0001` (rules in `schema.sql`) | `VALIDATION` |
  | `23503` | `NOT_FOUND` |
  | Anything else | `UNKNOWN` |

  Database rules keep their own human message. Every other code gets a plain message: constraint names and
  database internals are never shown.
- The gateway's upload and download methods throw these through `sbOk`. The outbox logs the failure, keeps the
  change and retries.
- `shared/logging/logger.js` (`logger.error/warn/info`) is the only place that writes to the console.

## Configuration and secrets

- `config.js` holds the Supabase URL and the **publishable** key. Both are public by design, because the database
  is protected by RLS.
- `shared/config/app-config.js` is the only module that reads `config.js` or the test flag. It exports:
  - `sbUrl`, `sbKey`, `cloudWanted`, `cloudConfigured` and `HOME_URL`;
  - `APP_ENV`: `test` under the browser tests, `development` on localhost, and `production` otherwise.

  The test hook is installed only under `test`. The module needs no `window`, so unit tests import it in Node.
- **Never in the frontend:** the service-role key, OCR/extraction provider keys, or any other secret. Server-side
  secrets belong in Supabase Edge Function secrets, called through `infrastructure/supabase`.

## Security

- **Tenant isolation is enforced by the database.** Every `hangtag_*` table has the RLS policy "Own rows only"
  (`owner_id = auth.uid()`), and signed-out requests are refused. Frontend filtering is never the protection.
  Tests: `supabase/tests/legacy_schema.test.mjs` and `legacy_variants_migration.test.mjs`, plus the two-account
  and two-device browser tests.
- **The Phase 1 foundation** (`supabase/migrations/`) isolates by shop membership (`is_shop_member`). It is tested in
  `supabase/tests/phase1_foundation.test.mjs` but not applied to the live project.
- **Per-account local data.** On a shared device, each account's local data is kept separately and swapped on
  sign-in (`features/auth/services/account-data.js`).
- **HTML escaping.** Every interpolated value goes through `esc()`.
- **Test hook.** `window.__ev` is installed only when a test sets `window.__HANGTAG_TEST__` before the app loads.

## PWA and service worker

- `sw.js` serves the saved copy first and refreshes it in the background. Supabase requests always go to the network.
- The service worker saves the app shell plus every module and stylesheet under `src/`. Its cache name is a hash of
  those files, so each deploy installs a complete new offline copy and removes the old one.
- The service worker holds no business logic. Offline behaviour for data (queueing, retries) lives in `features/sync`.

## Build

`npm run build` (`scripts/build.mjs`) runs these steps:

1. Regenerates the module list in `src/app/test-hook.js`.
2. Regenerates the offline file list and cache name in `sw.js` (between `BUILD:START` and `BUILD:END`).
3. Runs the architecture check.
4. Bundles `src/app/main.js` with esbuild into `dist/` (gitignored, not deployed). This proves every import resolves
   and every module parses.
5. Runs ESLint (`eslint.config.js`): undefined names (a missing import) and unused variables are errors.

`npm run check` runs the same steps but fails instead of writing, and the unit tests run it. **Run `npm run build`
after changing any file under `src/`, and commit the updated `sw.js` with it.**

## Testing strategy

| Kind | Where | What |
|---|---|---|
| Unit | `tests/unit` | `domain.test.mjs`: domain rules. `use-cases.test.mjs`: use cases with fake ports. `infrastructure.test.mjs`: the gateway against a fake client, mappers, error mapping, repositories. `ports.test.mjs`: the ports registry, render bus and persistence. `architecture.test.mjs`: layer rules, no cycles, test API. `build.test.mjs`: `npm run check` (offline list, bundle, lint) |
| Database | `supabase/tests` | Schema, RLS isolation, triggers and migrations, on PGlite with Supabase stubs |
| Integration (app ↔ cloud) | `tests/e2e/cloud-roundtrip.test.mjs` | Two devices sync through the real supabase-js against a stand-in PostgREST that rejects unknown columns |
| E2E | `tests/e2e` | Sign-in (Google, email, tabs), per-account data, offline queue and service worker, POS flows (variants, returns, exchanges, receipts), shop setup and settings |

Commands:

- `npm test` runs everything.
- `npm run test:unit`, `npm run test:db` and `npm run test:e2e` run one group.
- `npm run lint` runs ESLint on its own.

E2E tests need Chrome (set `CHROME_PATH` to override) and serve the repository on `http://localhost:3210`.

The browser tests call app internals through `window.__ev`. The names they use are listed in
`tests/test-api.json` and checked by `scripts/test-api.mjs`. When you move a function, keep it exported under the
same name.

## Adding a feature (how later phases plug in)

1. **Domain first.** Put models and rules under `domain/<area>/`: pure functions, unit-tested in Node. For example,
   options and variant combinations go in `domain/catalog/`, and barcode check digits in `domain/catalog/barcode.js`.
2. **Ports for anything outside the app.**
   1. Declare the contract in `shared/di/ports.js`.
   2. Implement it under `infrastructure/`.
   3. Provide it in `app/container.js`.
   4. Add a one-line accessor in the feature's `repositories/` (or `services/`).
   5. Give unit tests a fake with `override()`.
3. **Use cases** go under `features/<feature>/use-cases/`. They validate with domain rules, call ports, and return
   `{ error }` or a result. They never build HTML.
4. **UI** goes under `features/<feature>/pages|components/`. Wire clicks in `app/events/dom-events.js` (delegated
   `data-*` attributes), escape all markup with `esc()`, and call use cases.
5. **Database changes** go in a new file under `supabase/migrations/` (or `supabase/schema.sql` while the live app
   still uses it), with RLS on every table and a test in `supabase/tests/`. Map rows in
   `infrastructure/supabase/mappers.js`, and add the gateway methods to `cloud-gateway.js`.
6. **Tests.** Add unit tests for rules and use cases, database tests for schema changes, and an e2e test for the
   main workflow.
7. Run `npm run build`, then `npm test`.

Phase 3 and 4 were added this way:

- **Options and variants:** rules in `domain/catalog/options.js` (catalog v3: `opts` + variant `o`); the editor calls its pure
  operations; `save-product.js` saves through `productRepository`; the database stores `options.opts` and `option_values`.
- **Barcode / QR:** code generation in `domain/catalog/barcode.js`; drawing behind `barcodeService` / `qrCodeService`.
- **Supplier bills:** planning in `domain/inventory/bill-import.js`; reading behind `documentExtractionService` (an Edge
  Function holds the provider key); saving behind `inventoryImportService` (one database transaction). A different OCR
  provider only needs a new provider file in `supabase/functions/extract-bill/providers/`.
